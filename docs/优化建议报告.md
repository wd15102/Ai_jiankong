日期：2026-09-13
范围：webapp.js / webhook.js / monitor.js / lib/（store.js、ai.js、push.js、ys7.js、judge.js）/ webapp.html
说明：全部结论基于逐行核对源码，行号以当日文件为准。此前《代码审查报告》(docs/代码审查报告.md) 中的多数 P0/P1 已修复，本报告只列"仍然存在的优化点"，并注明哪些已确认修好、不必重复劳动。

## 一、总体评价

- **架构合理**：三进程分工清晰（webapp :8790 看板 / webhook :8787 推送回调 / monitor watch 轮询告警），无框架依赖，仅一个真实第三方依赖（jimp）。
- **核心正确性有保障**：跨进程共写 data/events.json 已统一收敛到 lib/store.js 的"文件锁 + 读-改-写事务"，锁重入保护、带 pid 的临时文件、rename 失败回退、残锁回收等实现扎实，**未发现真正的竞态丢事件 bug**，是全项目质量最高的模块。
- **历史审查的多数问题已落地修复**（见第五节），代码整体处于"可用且稳健"状态，剩余问题集中在：网络调用无超时、个别注入面、性能热路径、以及运维层空白。

## 二、建议立即处理（P1）

1. **lib/ai.js:28 —— AI 渠道请求无超时**
   fetch 调 /chat/completions 没有 AbortSignal。挂起的 AI 请求会拖住整条"抓图→分析→推送"链路（monitor/webhook 都同步等它）。
   修复：`signal: AbortSignal.timeout((p.timeoutSec || 90) * 1000)`，并在渠道失败冷却逻辑里区分"超时"与"报错"。

2. **lib/ai.js:54 —— 整图同步读取，无存在性/大小校验**
   `fs.readFileSync(imageFile).toString("base64")` 前不检查文件是否存在、多大。抓图来自萤石云端，异常大图（几十 MB）会整体 base64 进内存，有 OOM 风险；文件不存在则直接 ENOENT 崩到外层。
   修复：读取前 existsSync + statSync，超过上限（如 8MB）直接返回 {ok:false}。

3. **lib/ys7.js:9/29、lib/push.js:9/60/79/85/138/188 —— 所有外呼 fetch 均无显式超时**
   ys7 与 push 里全部 fetch 都没有 AbortSignal（Node/undici 默认超时在 300 秒量级，对交互链路等于挂死）；ys7.js:29 downloadTo 抓图下载也没有大小上限。
   修复：统一加 `AbortSignal.timeout(30000)`（token/告警/云台）与 60000（下载）；下载按 Content-Length 或流式截断限制体积。

4. **lib/push.js:190 —— 不可信标题直入 HTTP 请求头（Header 注入面）**
   ntfy 推送把 title 放进 `headers: { "Title": title }`，title 来自 AI 结论/微信侧内容，含 CR/LF 时可注入请求头。
   修复：`String(title).replace(/[\r\n]+/g, " ").slice(0, 100)`。

5. **lib/push.js:60 等 —— appSecret / access_token 拼在 GET query**
   这是微信公众平台 API 自身的调用方式（无法改 header），真正风险是**日志与代理侧泄露完整 URL**。
   修复：全项目确认不打印含 secret/token 的 URL；现有 console 日志若有 URL 输出需脱敏；怀疑泄露时及时轮换 AppSecret。

6. **webapp.html —— 前端全部 fetch（13 处）无超时**
   webapp 接口卡住时看板按钮会永远转圈（抓图/分析接口背后还串着 AI 调用）。
   修复：封装一个 `fetchT(url, opts, ms)` 工具函数，内部 AbortSignal.timeout(15000)，替换所有裸 fetch。

7. **webhook.js /ezviz/push —— 未配置 ezvizPush.secret 时放行不校验**
   代码已有醒目告警，但报告必须强调：上线前必须配置该密钥，否则"人员活动"告警可被伪造进家庭推送链。

## 三、短期优化（P2）

8. **webapp.js /api/push-log 全量扫盘无缓存**：前端每 30 秒轮询一次，每次都对 captures/ 与 motion 目录做全量 readdir/stat。建议按目录 mtime 做 60 秒级结果缓存。
9. **webapp.js 启动串行抓图**：启动时对每台 watch 设备依次抓图，设备多时启动明显变慢。建议并行化（Promise.allSettled）或延后到首个请求。
10. **webhook.js 推送图片加载失败无降级**：图片读取失败时模板消息留黑屏。建议失败自动降级为纯文字推送（带事件摘要）。
11. **monitor.js watch 看门狗无重入保护**：30 分钟 watchdog 定时器触发时上一轮可能仍在跑，建议加 running 标志。
12. **30 分钟节流策略各渠道不一致**：同一事件在不同通道重复度不同，建议统一到 push 层单点节流。
13. **微信模板推送"全渠道失败"无整链重试**：建议失败事件入重试队列（如 1/5/15 分钟三次）。
14. **删除调度与图片计数不同步**：按"图片数"删与按"事件数"删的两套调度会产生"有记录无图"事件（看板显示"无截图"，已有 sameEvent 防误删兜底，但口径宜统一为事件维度）。

## 四、中长期技术债（P3）

15. **lib/store.js:206 契约偏差**：updateJson 文档承诺"其他返回值→使用原地修改后的数组"，实现返回的是 mutate 的返回值 r（当前全部调用方走副作用，无实际影响）。改文档或改实现，避免未来新调用方踩坑。
16. **lib/judge.js:36**：POS_ABNORMAL 含裸词"注意/需关注"，正常描述也会被标"异常"，增加看板噪声。建议收窄为危险词邻近匹配。
17. **依赖治理**：jimp 引入 image-q/panojs/pngjs/canvas 等重型传递依赖，lockfile 未锁版本且可能存在已知漏洞。建议 `npm audit` + lockfile 固化 + 评估是否可用 jimp 的按需子模块或直接删除该依赖。
18. **运维空白**：*.run.log 无限增长（需 logrotate 或按大小切割）；data/events.json 无定期备份（store.js 的 .bak 只保最近一份）；.corrupt 归档按 60 秒节流留档会缓慢累积；缺少优雅停机与"反拓扑顺序"的三进程启停脚本。
19. **模块化**：webhook.js 单文件过大（2000+ 行），建议按"回调协议解析 / 推送编排 / AI 编排 / 日报"拆到 lib/ 子模块。
