## 二、P0 必修

### P0-1　CSRF：任意网页可一键清空你的全部历史记录

**位置**：`webapp.js:36-49`（`tokenGate`）

```js
function tokenGate(req, u, res) {
  const p = u.pathname;
  const sensitive = PROTECTED_PATHS.indexOf(p) >= 0 || p === "/__shutdown" || p === "/__who";
  if (!sensitive) return false;
  if (isLoopback(req)) return false;      // ← 本机请求直接放行
  if (API_TOKEN && u.searchParams.get("token") === API_TOKEN) return false;
  ...
}
```

**问题**：`isLoopback` 的放行逻辑对「浏览器发起的跨站请求」同样生效。攻击链：

1. 家人在浏览器里打开任意一个恶意/被挂马的网页；
2. 该网页执行 `fetch('http://localhost:8790/api/events/delete-all', {method:'POST', mode:'no-cors'})`；
3. `Content-Type` 缺省为 `text/plain` → 属于 CORS **简单请求**，不触发预检；
4. `/api/events/delete-all` 的处理器（`webapp.js:521-527`）**不读 body、不校验 Content-Type**，直接 `saveEvents([])` + `saveAlarmState(...)`；
5. 459 条历史 + `alarm_state` 全部清空，浏览器控制台里连报错都没有。

同一漏洞可无感触发 `/api/capture`（烧萤石抓图配额）、`/api/analyze`（烧 AI 额度）、`/api/alarms/check`。

**修复**：在 `tokenGate` 里，对敏感路径先做同站校验，再做 loopback 放行。

```js
// 跨站请求识别: 浏览器发的跨站请求一律拒绝(与是否本机无关)
function isCrossSite(req) {
  const site = req.headers["sec-fetch-site"];
  if (site && site !== "same-origin" && site !== "none") return true;  // none = 用户直接敲地址栏
  const origin = req.headers.origin;
  if (origin) {
    try { if (new URL(origin).host !== req.headers.host) return true; }
    catch (e) { return true; }
  }
  return false;
}

function tokenGate(req, u, res) {
  const p = u.pathname;
  const sensitive = PROTECTED_PATHS.indexOf(p) >= 0 || p === "/__shutdown" || p === "/__who";
  if (!sensitive) return false;
  if (isCrossSite(req)) {                          // ← 新增: 跨站一律拒
    sendJson(res, 403, { error: "跨站请求被拒绝" });
    return true;
  }
  if (req.method === "POST" && !/^application\/json/.test(req.headers["content-type"] || "")) {
    sendJson(res, 415, { error: "需要 Content-Type: application/json" });  // ← 抬出简单请求范畴
    return true;
  }
  if (isLoopback(req)) return false;
  if (API_TOKEN && u.searchParams.get("token") === API_TOKEN) return false;
  sendJson(res, 401, { error: "未授权：非本地访问需在 URL 携带 ?token=<webapp.apiToken>" });
  return true;
}
```

前端 `webapp.html` 的 `deleteAllEvents()` 需要补上 `headers: {"Content-Type":"application/json"}`（`deleteEvent`/`deleteSelected` 已经带了）。

### P0-2　`events.json` 三进程并发写，会静默丢事件　✅ 已修复（2026-09-12）

**位置**：`monitor.js:55-77`、`webhook.js:197-211`、`webapp.js:108-121`（修复前）

三个 Node 进程各自 `loadEventsArr() → push → saveEventsArr()`，全程无锁。典型丢数据时序：

```
webhook : 读到 459 条  ─┐
monitor : 读到 459 条  ─┤  (同时)
webhook : 写入 460 条  ←┘
monitor : 写入 460 条     ← webhook 那条被覆盖，永久丢失
```

代码里已经写了「解析失败则把损坏文件另存为 `.corrupt.<ts>`」的兜底 —— **这个兜底本身就是并发写已经出过事的证据**。

#### 真正的根因比"没加锁"更深一层

`webhook.js` 的推送链路是 **读(第309行) → 下载报警图/复用存图/兜底抓图(多个 `await`) → 写(第377行)**，
中间隔了几百毫秒到几秒。也就是说这份"读到的全量数组"在写回去的时候**早就过期了**，
期间 webapp/monitor 追加的任何事件都会被整份覆盖。这比"两个写同时发生"的概率高得多——
它不是窄窗口竞态，而是必然丢失。`refreshTodayEvents` / `collectWindowEvents` 同样是"读 → 循环里 await 下载图片 → 写"。

所以只加一把锁不够，还必须把**读和写绑成一个事务**：锁内重新读最新内容再改。

#### 还有个被忽略的第二竞态源：共用的临时文件名

三个进程原本都写 `events.json.tmp`：并发时两个进程会往**同一个 tmp 文件**里交错写，
谁先 `rename` 谁就把对方的半截内容发布出去。改名原子性只保证"读方不会读到半截"，
并不保证"写方之间不互相踩"。现在 tmp 名带 pid。

#### 实际修复方案：`lib/store.js`（新增）

一个通用的「跨进程文件锁 + 读-改-写事务」模块，三个服务共用同一把锁：

```js
// 事务式提交: 加锁 -> 锁内重读最新内容 -> mutate(arr) 原地改 -> 原子落盘 -> 解锁
await store.updateEvents(ROOT, function (arr) {
  arr.push(newRec);   // mutate 必须是同步函数, 里面不能有 await
  return true;        // 返回 false = 内容无变化, 不写盘
}, { cap: store.eventCap(cfg) });
```

调用点全部改成"先做完异步准备（下载图片/调 AI），最后一次提交"：

| 文件 | 原写法 | 现写法 |
|------|--------|--------|
| `webhook.js` 推送落库 | 读(309) → await 下载图片 → 写(377) | 只读快照判定去重 → await 下载 → `mutateEvents` 提交，**锁内复查去重** |
| `webhook.js` `analyzeAndStore` | 读 → 改 → 写 | `mutateEvents` 锁内定位记录再改 |
| `webhook.js` `recordKanjiaCapture` | 读 → 判断幂等 → 写 | `mutateEvents` 锁内判幂等再追加（函数改为 async） |
| `webhook.js` `refreshTodayEvents` | 读 → 循环 await 下载 → 写 | 收集 `pending[]` → 一次提交，锁内按 `serial@ts` 复查 |
| `webhook.js` `collectWindowEvents` | 同上 | 同上 |
| `webapp.js` `recordEvent` | 读 → push → 写 | `mutateEvents` 追加 |
| `webapp.js` `deleteEventByFile` | 读 → filter → 写 | `mutateEvents` 锁内原地 splice |
| `webapp.js` `/api/analyze` | 读 → 改或新增 → 写 | 一个事务内完成"有则更新、无则新增" |
| `webapp.js` 删除/清空接口 | 读 → filter → 写 | `mutateEvents`；拿不到锁时返回 500 而不是假装成功 |
| `monitor.js` `recordEvent` | 读 → push → 写 | `mutateEvents` 追加 |
| `tools/rejudge_events.js` | 自己重新读一遍再按键合并 | 走同一把锁 |

顺带修掉 `storage.eventRetention` 只有 1/3 生效的问题（P1-7）：保留上限统一由 `store.eventCap(cfg)` 提供。

#### 踩到的三个坑（都已修，写在这里免得以后重犯）

1. **Windows 上 `fs.openSync(path, "wx")` 在文件已存在时返回 `EPERM` 而不是 `EEXIST`**
   （Node 在 Windows 上 `O_CREAT|O_EXCL` 的已知行为）。最初把"非 EEXIST"当成致命错误直接返回失败，
   结果正常的锁竞争被判成写失败 → 每轮压测静默丢 1~2 条。现在 `EEXIST/EPERM/EACCES/EBUSY` 一律按"被占用"重试。
2. **`fs.unlinkSync` 删锁文件会偶发 `EPERM`**（被杀软/索引短暂占用）。如果放任失败，本进程自己的锁会残留，
   下次抢锁时撞上"持锁者 = 自己"而僵住。现在释放带重试，并且抢锁时若发现**持锁 pid 就是自己**，判定为上次释放失败的残留、直接接管。
3. **不能把"持锁进程还活着"的锁按年龄抢走**。现在抢锁前先读锁内容，用 `process.kill(pid, 0)` 判断持锁进程是否存活：
   死了才抢（实测 9ms 自愈），活着就老实等 —— 否则会出现两个进程同时以为自己持锁。

锁实现上没用忙等（会打满 CPU），也没用同步自旋（会阻塞事件循环，最要命的是会把萤石推送的 2 秒应答挤掉）。
抢锁是 `async` 的、带抖动退避，事务体本身仍然全同步，所以"拿到锁"到"释放锁"之间没有 `await`，本进程不会并发进入同一文件的事务。

#### 实测验证

```
node tools/stress_events.js 6 120     # 6 进程 × 120 条并发写, 对照组 vs 实验组
对照组 无锁: 落盘 32 条 / 期望 720      丢失 688 条  FAIL
实验组 加锁: 落盘 720 条 / 期望 720     丢失 0 条    PASS   放弃写入 0 次
```

`tools/stress_events.js` 已作为这个 bug 的回归测试保留，改动 `lib/store.js` 后请重跑。

集成层面（用真实 `events.json` 的副本、三个进程分别模拟推送/AI回写/监控追加三种写法）：
落盘条数、唯一 file 数、基线记录保留、锁内去重跳过次数全部符合预期，结束后无残留 `.lock` / `.tmp`。

> **注意**：修复只在**三个服务都重启之后**才生效。旧进程仍然是无锁写入者，
> 在它们退出之前，并发丢事件仍可能发生。

**关于 `push_throttle.json`**：同一类问题（`lib/push.js` 直读直写 vs `webhook.js` 的 `_throttleCache` 内存缓存，两套格式互相覆盖）尚未处理，见 P1-6。
`lib/store.js` 的 `updateJson(file, mutate)` 是通用的，迁移过去只是几行的事。

**曾被考虑但未采用的方案**：让 `webhook.js` 成为唯一写入者、其余进程走 `POST /api/internal/event` 落库。
它能彻底消灭文件级并发，但给 monitor 这条"本地直写"的路径引入了对 webhook 进程可用性的依赖 ——
webhook 挂了就完全无法记录事件。文件锁方案没有这个耦合。

### P1-2　公网隧道侧 webhook 完全无鉴权

`webapp.js` 做了 `tokenGate`，但 `webhook.js`（8787，也就是花生壳对外暴露的那个端口）**一个鉴权都没有**：

| 路径 | 现状 | 风险 |
|------|------|------|
| `GET /api/ptz?serial=xx&dir=up` | 无鉴权，只判断 `ptz:true` | **任何人拿到域名就能远程转动你家摄像头** |
| `GET /api/live-url?serial=xx` | 无鉴权，直接返回 HLS 播放地址 | 直播流被直接取走，绕过隧道 |
| `GET /captures/xxx.jpg` | 无鉴权（文件名是唯一门槛） | 现场照片可被枚举/遍历 |
| `GET /detail?file=xxx` | 无鉴权 | 同上，还带 AI 结论 |
| `GET /history`、`/today` | 无鉴权 | 全家活动时间线可看 |

`/__shutdown` 做了「远程必须带 token」是好的，但其余接口没跟上。这些接口是给家人用的，靠「域名不公开」当安全边界。

**修复（最小代价）**：复用 webapp 的签名 token 思路，给 webhook 加一个可选开关，默认关闭以不破坏现有家人链接：

```js
// config.json -> wxServer.publicToken: "随便一串随机字符"
// 家人链接改为 https://域名/live?serial=BK2385850&k=<token>
// 未配置 publicToken 时行为不变(向后兼容)
function publicGate(req, u, res) {
  const need = (cfg.wxServer && cfg.wxServer.publicToken) || "";
  if (!need) return false;
  if (isLoopback(req)) return false;
  const k = u.searchParams.get("k") || u.searchParams.get("token") || "";
  if (k === need) {
    // 通过后种 cookie, 后续 /captures/、/detail 不用每张图都带参数
    res.setHeader("Set-Cookie", "kj=" + need + "; Path=/; Max-Age=2592000; SameSite=Lax");
    return false;
  }
  if ((req.headers.cookie || "").indexOf("kj=" + need) >= 0) return false;
  res.writeHead(403); res.end(""); return true;
}
```

**至少**要给 `/api/ptz` 加鉴权——转云台是可写操作，性质和「看照片」完全不同。

### P1-3　判人逻辑 4 份实现，已经不一致了

| 位置 | 实现 | 差异 |
|------|------|------|
| `monitor.js:91-102` | `judgePerson()` | `abnormal` 只排 `无异常` |
| `webapp.js:124-132` | `judgePerson()` | `abnormal` 排了 4 种否定式（`无异常/没有异常/看不到异常/未发现异常`） |
| `webhook.js:384-386` | 内联 `noPerson` / `hasAbnormal` | 又一套正则 |
| `webhook.js:458` | `rec.person = /有人/.test(txt)` | 最粗暴的一版，**会把「无人」判成有人**么? 不会，但「未见人员」会 |

同一句 AI 结论经不同入口会产生不同判定。**实测复现**（直接跑 `monitor.js` 的判定逻辑）：

```
X 误判有人  <- 画面中未发现人员活动
X 误判有人  <- 未见人员活动
OK 正确无人  <- 【无人】画面安静
X 误判有人  <- 没有人          ← 因为「没有人」里包含子串「有人」
X 误判有人  <- 院子里没有人
OK 正确有人  <- 有人从画面经过
```

根因是 `/^\s*无人/` **没有 `m` 多行标志**，只能匹配整个字符串的**行首**；而 `judgePerson()` 接收的是完整多行内容。

为什么现在没有大面积误推？因为 `webhook.js` 调的是 `analyzeImageAI()`，`config.json` 的 prompt 要求「第一行必须输出有人或无人」，AI 绝大多数情况下把结论放在第一行行首，正好命中 `/^\s*无人/`。**但只要 AI 格式稍有漂移就会立刻误判**：

| AI 实际输出 | 判定 | 后果 |
|------------|------|------|
| `无人\n画面是空院子` | 无人 ✓ | 正常 |
| `【无人】画面是空院子` | 无人 ✓ | 正常（有括号）|
| `画面中未发现人员活动` | **有人** ❌ | 半夜误推送 |
| `没有发现可疑人员` | **有人** ❌ | 误推送 |
| `判断结论：无人\n画面为空` | **有人** ❌ | 结论在行首之后，落进关键词分支 |

注意 `webapp.js` 那一版多了 `negated` 处理，但**只作用于 `abnormal`，没作用于 `person`** —— 同一个洞。

**这就是误推送的直接来源**：家里没人，AI 说「未发现人员活动」，判定成「有人」，全家手机一起响。

**修复**：抽成 `lib/judge.js`，四个地方统一引用，并修正否定式：

```js
// lib/judge.js —— 唯一的判人实现
function judgePerson(content) {
  const c = String(content || "").trim();
  // 1) 显式标记优先
  const m = c.match(/【(有人|无人)】/);
  if (m) return { person: m[1] === "有人", abnormal: judgeAbnormal(c) };

  // 2) 否定式优先判定为「无人」: 覆盖 "未见/未发现/没有/无" + 人员类词
  const NEG = /(未|没有|无|没|不见|看不到|未发现)\s*(见|发现|出现|检测到)?\s*(任何人|人员|人影|人形|人)/;
  const POS = /(有人|检测到人|出现人|一个人|人形|人员活动)/;
  if (NEG.test(c)) return { person: false, abnormal: judgeAbnormal(c) };

  return { person: POS.test(c), abnormal: judgeAbnormal(c) };
}
function judgeAbnormal(c) {
  const NEG = /(无异常|没有异常|看不到异常|未发现异常|无危险|一切正常|平安无事)/;
  return /(异常|需关注|注意|陌生|闯入|可疑)/.test(c) && !NEG.test(c);
}
module.exports = { judgePerson: judgePerson, judgeAbnormal: judgeAbnormal };
```

`webhook.js` 里 `analyzeAndStore` 的 `rec.person = /有人/.test(String(txt))` 也要换成 `judgePerson(txt).person`。

### P1-5　`monitor.js` 轮询无重入保护

**位置**：`monitor.js:250-251`

```js
await round();
setInterval(round, interval);
```

一轮里如果有多条积压报警，每条都要「抓图 + 下载 + AI 分析」，单条耗时可能 5~25 秒；两台设备各来 3 条就超过 300 秒 → 下一轮 `round()` 已经在跑了，会出现**同一报警被两轮同时处理、重复抓图、重复推送**，而且会突破「免费版 100 次/天/设备」的抓图配额。

**修复**：

```js
let _rounding = false;
async function round() {
  if (_rounding) { console.log("[" + ts() + "] 上一轮尚未结束，跳过本轮"); return; }
  _rounding = true;
  try { ...原逻辑... } finally { _rounding = false; }
}
// 用固定间隔的 setTimeout 链更稳
async function loop() { await round(); setTimeout(loop, interval); }
loop();
```

顺带一提：`fallbackWarned = true` 之后**永不重置**，所以「报警列表接口降级」这种重要状态只会提示一次，之后即使反复降级也完全静默。建议改成「每轮失败都记一行，或每 30 分钟重复提醒一次」。

（日志里确实出现过一次 `[18:48:51] 报警列表不可用(code=50000)，降级为定时抓图模式`，说明这条路径被触发过。）

### P1-9　前端「新报警」红点会被后端定时器吃掉

**位置**：`webapp.js:456-464`

```js
let _lastEventCount = -1;
function detectNewEvents() {
  const count = loadEvents().length;
  const result = { hasNew: false, newCount: 0 };
  if (_lastEventCount >= 0 && count > _lastEventCount) { result.hasNew = true; result.newCount = count - _lastEventCount; }
  _lastEventCount = count;      // ← 每次调用都推进游标
  return result;
}
setInterval(detectNewEvents, 30000);   // ← 后端每 30 秒自己调一次
```

`/api/events/changed` 也调 `detectNewEvents()`，而前端 `webapp.html:659` 同样每 30 秒轮询一次。两个 30 秒定时器错开时：后端定时器先把 `_lastEventCount` 推到最新 → 前端下一次轮询拿到 `hasNew: false` → **红点永远不亮**。

**修复**：把「推进游标」和「读取增量」拆开，只有前端读取时才推进。

```js
let _lastSeenCount = -1;
function readNewEvents() {                     // 只读, 不推进
  const count = loadEvents().length;
  if (_lastSeenCount < 0) { _lastSeenCount = count; return { hasNew: false, newCount: 0 }; }
  return { hasNew: count > _lastSeenCount, newCount: Math.max(0, count - _lastSeenCount) };
}
function ackNewEvents(count) { _lastSeenCount = count; }   // 前端确认后再推进
```

顺带：`detectNewEvents()` 每次都 `loadEvents()` 全量解析。现在 238KB 还好，按 20,000 条上限涨到约 10MB 时，就是**每 15 秒解析 10MB JSON**。建议改成只记 `fs.statSync(events.json).size + mtimeMs` 做增量判断，不为数条数而全量解析。

### 2026-09-12　无截图记录（看板黑屏）修复

**现象**：看板「历史报警记录」里个别卡片是一块**纯黑**。实测 9/12 `07:31:50`、`07:48:34` 两条「人形检测」。

**根因**（三层，逐层查实）：

1. **记录的 `file` 是空串** —— 落库时就没拿到截图。
2. **为什么没拿到**：萤石对同一次活动会**连推数条**（人形标签消息 IntelligentTag **不带截图** + 智能侦测消息带截图），两条在同一秒内并发到达。日志与磁盘证据正好对上：

   | 时刻 | 日志 | events.json | captures/ |
   |---|---|---|---|
   | 07:31:50 | `已记录: …人形检测` | 有（`file=""`） | 没有对应图 |
   | 07:31:55 | `已记录: …智能侦测` | **不存在** | 有 `BG6569629_p1789169515000.jpg` |

   两条各自「读 → 下载图 → 写」并发交错：人形标签那条扫垫图时，智能侦测的截图**还在下载中**，扫不到；兜底抓图又失败 —— 而当时跑的版本（`v2026-09-11.32`）这条失败路径**完全静默**、没留日志。紧接着它写回 events.json，**把智能侦测那条记录整份覆盖掉了**（当时仍是无锁写入），于是图留在磁盘上成了孤儿、记录却没了。§七 的 store 事务修掉了"覆盖"，但"并发时序导致拿不到图"仍在。
3. **为什么显示成黑屏**：`webapp.html:590` 渲染卡片时无条件拼 `src="/captures/" + e.file`，空 `file` 请求 404；而 `.card img{height:180px;background:#0b0f14}` 让失败元素保留 180px 深黑底色 —— 就是那块黑。同一文件里推送记录页（`webapp.html:425`）早写了 `onerror="this.remove()"`，历史卡片漏了。

**改动**：

| 位置 | 改动 |
|---|---|
| `webhook.js` 事务内 | 同活动已有记录但**缺截图**时，把本次拿到的图**补到那条记录上**，而不是再加一条 |
| `webapp.html` 渲染 | 无 `file` 直接渲染「无截图」占位（不发无效请求）；有 `file` 但加载失败由 `onerror` 换成「截图已失效」 |
| `webapp.html` + `webapp.js` 删除 | 选中/删除改用 `设备@时间戳` 定位。原来用 `file` 做键，空串会互相顶掉 —— 多条无图记录只能选中一条，批量删除还会**误删全部无图记录**；接口新增 `items` 参数 |
| `tools/repair_noimage_events.js` | 存量修复：按「同设备 + 时间邻近」认领那张已躺在 `captures/` 里的孤儿图 |

**验证**：补图逻辑从源码提取后跑行为测试 **8/8**，含「旧记录 `person=false` + 本次自带截图必须放行新增」这条不能破坏的补救路径。
