## 一、项目定位

摄像头在湖南常德老家，服务跑在长沙电脑上。萤石云推送到达 → 自写算法预筛 → 视觉大模型判人 → 微信推送 + 公众号被动查询 + Web 看板。

**零框架依赖**（仅 `jimp` 一个依赖，用于图像解码），Node >= 18。

```

   ├─ ① 先秒回 {code:200, messageId}   ← 萤石硬要求 2 秒内响应，否则判推送失败

        人形格式归一化     IntelligentTag / PeopleDetectionEvent → SmartHumanDet
        ▼
        ┌─ 普通移动侦测 ────────────────────────┐

        │    命中车辆 → 升级为智能事件           │
        └────────────────────────────────────────┘
                      │ 升级
                      ▼
        三级选图（webhook.js:853-942）
           ⓪ 本地算法同一张图 → ① 报警自带截图 → ② HD 截帧 → ③ 垫图复用
                      ▼
        入库 events.json（store.js 跨进程事务）
                      ▼
```

## 四、萤石上报格式（2026-08 实测）

设备推送**免费**，但报文里只有 `pictureList[0].id`（设备 SD 卡里的文件名），**拿像素要另外调接口**。

### 三条取图路径

| 路径 | 配额 | 硬伤 |
|------|------|------|
| ① `streamer/alarm/url/get` | 不耗 | 依赖 SD 卡，离线/卡异常取不到 |
| ② `liveAddress` + ffmpeg 主码流 | 不耗 | 撞 **9048** 账号级并发观看限制 |
| ③ `/capture` = `client.capture` | **100 次/天/设备** | —— |

> **配额 = "平台替你拍照"的次数，跟设备推多少条无关。**

### 消息类型（18750 条实测）

| 类别 | 类型 | 条数 | 看板分组 |
|------|------|------|---------|
| 移动侦测 | `motiondetect` | 12672 | 移动侦测 |
| **人形** | `IntelligentTag`（多标签） | 1889 | 按 payload 分流 |
| | `SmartHumanDet` | 361 | 人形检测 |
| | `PeopleDetectionEvent` | 401 | 人形检测 |
| | `intelligentDetection` | 220 | 人形检测 |
| 宠物 | `PetDetection` / `pet_detection` / IntelligentTag(pet) | 932 / 742 / 1046 | 宠物侦测 |
| 车辆 | `SmartVehicleDet` | 463 | 车辆检测 |
| 设备状态 | `storage_status` / `IrcutFilterStatusChange` / `switch_*` / 上下线 | ~1100 | **看板全部丢弃** |

**`IntelligentTag` 是多标签上报**，标签在 `payload.intelligentTag.tags`：实测 1889 条 = `pet` 1046 + `human` 833 + `abnormal_voice` 10。

**`IntelligentTag` 是「活动片段型上报」**：一次持续活动期间每 ~30 秒重推一条，`startTime` 固定、`endTime` 延伸。看板按 `serial@startTime` 归并显示「合并 N 条·持续 N 秒」。

## 七、事件记录（events.json）

**唯一合法写入路径：`lib/store.js` 的跨进程事务**（文件锁 + 锁内重读 + 原子落盘）。三个服务共用同一把锁。

| 字段 | 含义 |
|------|------|
| `ts` / `time` | 毫秒时间戳 / `YYYY/M/D HH:mm:ss`（**月日不补零**） |
| `serial` / `name` | 设备序列号 / 名称 |
| `file` | 抓图文件名，**可能为空串**（无图记录） |
| `title` | 人形检测 / 定时存档 / 本地检测(疑似车辆) … |
| `provider` | **谁给的结论**：空 = 萤石设备端直通（从没跑过 AI）；非空 = 模型名 |
| `ai` | AI 结论文本；`(点击AI分析)` / `(等待分析...)` 是占位文案 = 无结论 |
| `person` | true/false 两态，**无第三态** |
| `pushed` | 是否已推送微信 |

**判读三态**：看板上「有人/无人/无AI结论」按 `ai` 字段判（`hasAiVerdict`），不能按 `person` —— events.json 的 person 只有两态，「无AI结论」的记录是 `person=true` + `ai` 占位文案。

### 数据文件

| 文件 | 内容 | 备注 |
|------|------|------|
| `data/events.json` | 事件记录 | 4997 条；`eventRetention:-1` 不限制 |
| `data/push_log.json` | 萤石推送原始报文 | `pushLogRetention:5000`（原 24MB 不封顶，单条落盘阻塞 221ms+）|
| `data/daily_reports/YYYY-M-D.json` | 日报存档 | **日期不补零** |
| `data/capture_quota.json` | 萤石抓图配额耗尽态 | 撞 10028 后当天停手 |
| `data/stream_backoff.json` | 9048 取流退避态 | 5→10→20→40 分钟递增 |
| `data/push_throttle.json` | 推送节流 | 时间戳数组 |
| `captures/` | 事件图 | `captureRetentionDays:0` 永久 |
| `captures/motion/` | 移动侦测临时垫图 | `motionRetentionHours:3` |

## 八、Web 看板功能

### 三个标签页

**1. 实时看板**
- 设备下拉 + 模型下拉切换
- 实时画面 + 「抓高清图」/「AI 分析」/「查报警」/「查今日有人」按钮
- 4 个统计卡：今日人员活动 / 覆盖设备 / 最后活动 / AI 分析率
- 历史报警区：全部/有人/无人筛选、卡片/列表视图、30 秒自动刷新、批量操作工具栏

**2. 萤石推送记录**
- 5 个统计块：推送总数 / 消息类型 / 涉及设备 / 最早-最新 / 已合并重复
- **四维组合筛选**（全部在服务端）：时间 × 类型 × 设备 × 是否有人
- 「已组合」chip 组：每个条件可单独点掉 + 清空全部
- 设备维度支持按村（双溪村/木山村）或按 serial（具体设备）
- 分组折叠 + 分页（100 条/页）

**3. 有人记录**
- 3 个统计：有人记录数 / 最活跃时段 / 最活跃设备
- 0-23 时直方图
- 按村 / 按时间 / 按任意日期筛选 + 加载更多

- 通道：`wxTest`（测试号模板消息）/ `wecombot` / `wxpusher` / `ntfy`

## 十三、配额账（重要）

**萤石免费版**：抓图 100 次/天/设备，全接口 1000 次/天/账号。

```
每设备配额分配（现状 config.watch.captureMinMinutes = 120）
  巡检存档   12 次  （2 小时/次）
  报警补图  ~50 次
  ────────────────
  合计       62 次 / 上限 100   → 余量 38 次
```

**2026-10-08 之前是 30 分钟/次 = 48 次，合计 98/100，余量仅 2 次 → 被打爆**：
`code=10028` 出现 589 次、`9048` 出现 803 次，monitor 高清截帧 574 次尝试成功 0 次。

### 9048 与 10028 是两回事

| 错误 | 含义 | 恢复方式 |
|------|------|---------|
| `9048` | 账号级**并发观看**限制 | 几分钟 → `stream_backoff.json` 递增退避 5→10→20→40 分钟 |
| `10028` | **当日抓图配额**耗尽 | 等次日 0 点 → `capture_quota.json`，当天停手 |

**已修的死循环**：9048 退避 → 跳过拉流 → 回落 `client.capture` → 爆 10028 → 更拉不到流 → 再退避。
现在退避期内 `captureHD` **直接抛错不再回落**（宁可无图也不烧配额）。

## 十四、环境约定

- **`.bat` 必须是 GBK + CRLF、无 BOM、不加 `chcp 65001`**（见 `docs/编码教训.md`）
- **`config.json` 含全部密钥**，已 gitignore 且从未进 git 历史。改配置后不要 `git add -f`
- **`webapp.html` 启动时读一次**，改前端必须重启 webapp，刷新浏览器没用
- **日志在 `data/` 下**（`webhook_run.log` / `monitor_run.log` / `webapp_run.log`）
- **任何带时间的排序必须用 `tsMs` 毫秒**，时间字符串月日不补零（`2026/9/30` vs `2026/10/8` 字典序会错）
- **判人逻辑只在 `lib/judge.js`**，不要在任何服务里另写判人正则

## 十五、排查手册

### 没消息类排查三步

1. **按 serial 分设备核对** —— 证明不是全链路断
2. **查 `data/push_log.json`** —— **唯一能证明"设备端到底有没有发"的证据**
3. **用 Read 直接看 `captures/` 的 jpg** —— 别只读 `ai` 文本

> `events.json` 只能证明"我们处理过"，**无法区分「没人经过」和「有人经过但系统没收到信号」**（2026-10-06 因此误判过一次）。

### 告警量变化归因

1. 按天 × 类型统计 —— **等比例缩水** vs **某类消失**（前者是场景/设备波动，后者才是限流/套餐）
2. 设备真掉线（注意 `NetworkStatusList` 是**多网卡快照**，`onlineStatus:0` 可能只是网线没插）
3. 同一 `alarmId` 重复组数 —— 判断是否被判推送失败/降级
4. `events.json` 有人事件数 —— 区分"真没人"与"有人但设备没报"

### 改动是否生效

- `http://127.0.0.1:8790/__who` 返回 `{version, pid}` —— 版本号还是旧的就是没重启
- 推送记录页页头「N / M 条」的 **M 是原始报文数**，M≈N = 归并没生效
- 改完 `webapp.html` 必跑 `node tools/check_webapp_syntax.js`
